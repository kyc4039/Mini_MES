# 문제 해결 기록 (STAR 형식, 기록용)

화이트(라이트테마) 버전부터 겪은 모든 시행착오를 빠짐없이 정리했다. 자기소개서용
소재를 고를 때 참고할 원본 자료이므로, 사소한 것까지 다 포함했다. 카테고리별로
묶었다.

---

## A. 데이터 정합성 / 로직 설계 문제

### A1. 투입 LOT 필터링 — 카테고리만 맞으면 다 뜨던 문제
- **S**: 화성충방전 단계에서, 이미 화성충방전이나 최종검사까지 끝난 셀이 다시 투입 후보로 뜸
- **T**: "정확히 바로 직전 공정에서 나온 LOT만" 인정하도록 필터를 정교화해야 함
- **A**: 처음엔 라벨에 "어느 공정 산출물인지" 표시만 추가(반쪽 해결) → 이후 `predecessors` 제약을 레시피에 추가해 근본 해결
- **R**: 여러 날짜·여러 배치가 쌓여도 정확히 직전 단계 결과물만 후보로 뜸

### A2. 스태킹처럼 투입 재료가 2종류일 때 하나만 없어도 폼이 열림
- **S**: 양극판 재고 0이어도 분리막만 있으면 등록 폼이 그냥 열려 혼란을 줌
- **T**: 부족한 재료를 정확히 짚어주는 경고가 필요
- **A**: `missing_input_categories()` 함수로 카테고리별 재고 유무를 따로 확인하는 로직 추가
- **R**: "OO 재고가 없다"는 구체적 경고 후 폼 자체를 숨김

### A3. 재고 초과 투입해도 그냥 저장됨
- **S**: 잔여 5kg인데 10kg 투입해도 검증 없이 저장돼 음수 재고가 될 수 있던 버그
- **T**: 저장 전 실제 잔여수량 검증 필요
- **A**: 트랜잭션 맨 앞에서 각 투입 LOT의 잔여수량을 조회해 초과분을 막고, 격리 테스트로 롤백까지 확인
- **R**: 초과 시 아무 것도 저장 안 됨(롤백), 정상/경계값은 그대로 통과

### A4. 대시보드 파이프라인 — "완료 개수 세기"의 함정
- **S**: 오늘 새로 믹싱을 시작했는데, 어제 이미 끝낸 코팅~최종검사가 계속 "완료"로 표시됨
- **T**: "오늘 새로 시작한 사이클"과 "예전에 끝난 사이클"을 구분해야 함
- **A**: 공정별 개별 비교 대신, "가장 최근 시작된 실적이 몇 번째 공정인지"를 기준점으로 삼는 방식으로 재설계
- **R**: 격리 시나리오 테스트로 검증, 실제로도 정확히 대기/진행중/완료가 갈림

### A5. 작업지시 진행률이 2%로 나와서 버그인 줄 알았던 것
- **S**: 셀 1개를 완주했는데 KPI가 2%(1/100)로 낮게 나와 당황
- **T**: 버그인지 정상 계산인지 판단 필요
- **A**: "공정 완료 여부"와 "계획수량 대비 실제 생산량"이 서로 다른 지표라는 걸 설명받고 이해
- **R**: 버그가 아니었음을 확인, 두 지표의 의미 차이를 명확히 구분해서 사용하게 됨

### A6. 결과수량이 자동으로 산출되지 않아 매번 손으로 계산
- **S**: 결과수량을 매번 직접 입력해야 해서 번거로움
- **T**: 투입량 기반으로 결과수량을 자동 계산하고 싶음
- **A**: 공정별 규칙을 `sum`(합계)/`fixed`(고정)/`carry`(이어받기) 세 가지로 일반화한 `suggest_output_qty()` 추가
- **R**: 결과수량 입력칸에 계산값이 기본으로 채워지고, 필요시 수정 가능하게 유지

### A7. LOT 번호 자동 생성 요청 (원재료입고, 극판/조립/화성 공통)
- **S**: 매번 LOT 번호를 직접 타이핑하는 게 번거로움
- **T**: 기존 LOT 번호 패턴을 보고 다음 번호를 자동 제안해야 함
- **A**: `suggest_next_lot_no()`로 정규식 기반 순번 추론 로직 구현
- **R**: 품목 선택만 하면 다음 번호가 자동 채워짐

### A8. CELL LOT 번호 체계 3단계 진화
- **S**: 초기 `CELL-SN-2026072201` 형식이 날짜/순번 경계가 안 보여 가독성이 떨어짐
- **T**: 더 읽기 쉽고 정보량도 많은 번호 체계 필요
- **A**: 하이픈 추가(2단계) → 공정영문태그까지 포함(`CELL-SN-STACK-260805-01`, 3단계)로 순차 개선
- **R**: LOT 번호만 봐도 어느 공정 산출물인지 바로 알 수 있게 됨, 순번 계산도 공정별로 자동 분리되는 부수효과

## B. Streamlit 프레임워크 특성 관련 문제

### B1. 위젯 값이 계속 "지금 시각"으로 리셋됨
- **S**: 시작시각을 09:00으로 입력해도 다른 위젯 조작 시 다시 현재시각으로 초기화됨
- **T**: 화면 재실행과 무관하게 값이 유지돼야 함
- **A**: 원인이 `key` 없이 `value=datetime.now()`를 매번 새로 계산해서 넘기는 것임을 파악, `session_state` + `key`로 해결
- **R**: 다른 위젯을 조작해도 시각이 유지됨

### B2. `st.form` 안에서 동적 위젯(투입 LOT별 수량칸)이 안 늘어남
- **S**: 투입 LOT을 여러 개 선택해도 수량 입력칸이 그 개수만큼 안 늘어남
- **T**: 폼 제출 전에도 선택에 따라 위젯이 즉시 늘어나야 함
- **A**: `st.form`이 내부 위젯 변경 시 재실행을 억제한다는 프레임워크 특성을 파악, 폼 없이 일반 위젯+버튼 조합으로 구조 변경
- **R**: 선택 즉시 수량 입력칸이 정확히 늘어남

### B3. `RecursionError: maximum recursion depth exceeded`
- **S**: `st.Page()`로 네비게이션 구성 후 실행하니 무한 재귀 에러 발생
- **T**: 원인 파악 및 구조 수정 필요
- **A**: 진입점 파일이 자기 자신을 페이지 목록에 넣고 있었음을 발견, 진입점(`main.py`)과 페이지 내용 파일을 분리
- **R**: 정상 실행됨, 이후 페이지 추가 시에도 같은 실수 방지

### B4. 마크다운 색상 문법(`:orange[]`)이 HTML과 섞이면 안 먹힘
- **S**: 상태 텍스트에 색을 넣으려 `:orange[점검중]` 썼는데 화면에 문자 그대로 출력됨
- **T**: 정렬을 위해 HTML로 감싸면서도 색이 정상 표시돼야 함
- **A**: raw HTML 안에 마크다운 확장 문법을 섞으면 처리가 안 된다는 걸 파악, HTML `<span style="color:...">`로 전면 통일
- **R**: 정렬과 색상 둘 다 정상 동작

### B5. `st.metric`으로는 가운데 정렬이 안 됨
- **S**: KPI 카드를 가운데 정렬하고 싶었으나 `st.metric`엔 관련 옵션이 없음
- **T**: 대안 필요
- **A**: `st.metric` 대신 라벨+값을 직접 HTML로 그리는 커스텀 카드 함수로 전환
- **R**: 원하는 정렬 완전히 구현, 이후 모든 카드가 이 패턴 사용

### B6. 카드/리스트 여백이 위젯 조합에 따라 들쭉날쭉함
- **S**: `st.subheader()`+`st.markdown()`을 섞어 쓰니 카드마다 여백이 불규칙
- **T**: 일관된 여백 필요
- **A**: 제목까지 포함해 카드 전체를 HTML 문자열 하나로 합쳐 `st.markdown()` 한 번만 호출하는 패턴으로 통일
- **R**: 이후 모든 카드의 여백이 일관되게 통제됨

### B7. 리스트 데이터가 늘어나면 카드 높이가 계속 커짐
- **S**: 설비현황·최근생산실적 카드가 데이터 양에 따라 크기가 변함
- **T**: 고정 크기 + 스크롤 필요
- **A**: `st.container(height=N)` 적용 (CSS `overflow-y` 대신 Streamlit 내장 기능 활용)
- **R**: 데이터가 아무리 늘어도 카드 크기 고정, 스크롤로 처리

## C. UI/디자인 반복 개선

### C1. 대시보드 셀 박스 구분 — divider에서 카드로
- **S**: `st.divider()`만으로는 섹션 구분이 약함
- **T**: 카드 형태로 명확히 구분하고 싶음
- **A**: `st.container(border=True)`로 각 섹션을 카드화
- **R**: 시각적으로 섹션이 명확히 구분됨

### C2. 설비현황 표시 방식 여러 차례 개선
- **S**: 처음엔 전체 설비를 dataframe으로 나열, 이후 상태 텍스트가 안 뜨는 문제까지 발생
- **T**: 예외(비RUN)만 보여주고 상태를 색으로 구분해야 함
- **A**: `equipment_exceptions()` 쿼리로 예외만 조회 + HTML span 색상으로 표시 (마크다운 색상 문법 실패 후 전환)
- **R**: 점검중/정지만 눈에 띄게 표시, 나머지는 "그 외 N대 가동중"으로 요약

### C3. 공정별 불량현황 — 절대건수에서 불량률(%)로 전환
- **S**: 불량 "건수"만 비교하니 검사 10번 중 1번 FAIL과 1번 검사해서 1번 FAIL이 똑같이 보임
- **T**: 실제 심각도를 반영한 비교가 필요
- **A**: FAIL 개수와 전체 검사 개수를 함께 조회해 불량률(%)로 재계산, 막대 길이도 비율 기반으로 변경
- **R**: 심각도가 높은 공정이 실제로 더 길게 표시됨

### C4. 각 페이지 타이틀을 색상/그라디언트로 구분
- **S**: 6개 페이지 배너가 전부 같은 색이라 구분이 안 됨
- **T**: 페이지 성격에 맞는 시각적 구분 필요
- **A**: 처음엔 단색 배경 시도 → 대시보드와 톤을 맞추기 위해 같은 계열 그라디언트로 재통일
- **R**: 6개 페이지가 각자 고유 색상을 가지면서도 톤이 일관됨

### C5. KPI 카드 왼쪽 컬러 라인 시도 후 반려
- **S**: KPI 카드가 밋밋하다는 의견 제시
- **T**: 개선 방향 탐색
- **A**: 왼쪽 컬러 라인 스타일을 목업으로 제안하고 실제 적용까지 했으나
- **R**: 최종적으로 마음에 안 들어 원복 — 시도했다가 되돌리는 것도 정상적인 의사결정 과정임을 보여주는 사례

## D. 자잘한 문법/오타 실수

### D1. `NameError: CARD_TITLE is not defined`
- **S**: 코드 복사 과정에서 상단의 템플릿 문자열 정의 줄이 누락됨
- **T**: 원인 파악 및 수정
- **A**: 정의 위치와 재사용 구조를 설명하고 누락된 줄을 다시 제공
- **R**: 정상 동작, 이후 "전체 파일 통째로 덮어쓰기"를 권장하는 계기가 됨

### D2. `.keys()`를 `.key()`로 오타
- **S**: `AttributeError: 'dict' object has no attribute 'key'`
- **T**: 원인 파악
- **A**: 파이썬 딕셔너리 메서드가 복수형이라는 점을 안내
- **R**: `s` 추가로 해결

### D3. 삼항 조건식에 `=`와 `==` 혼동
- **S**: `if row.judge = "PASS" else ...`에서 문법 오류
- **T**: 원인 파악
- **A**: 대입 연산자와 비교 연산자의 차이를 설명
- **R**: `==`로 수정 후 해결

### D4. f-string 앞에 `f` 누락
- **S**: `{process_name}`이 변수값이 아니라 문자 그대로 화면에 출력됨
- **T**: 원인 파악
- **A**: f-string 접두사 규칙을 설명
- **R**: `f` 추가로 해결

### D5. 함수 중복 정의로 최신 버전이 무시됨
- **S**: 시간 기반 파이프라인 로직을 두 번 고쳐 드렸는데도 화면이 안 바뀜
- **T**: 원인 파악
- **A**: 파일 안에 같은 이름의 함수가 두 번 정의돼 있어 나중 정의만 조용히 적용된다는 파이썬 특성을 확인 (실제로 사용자 파일을 직접 열람해서 발견)
- **R**: 중복 제거 후 정상 반영, "화면이 안 바뀌면 중복 정의부터 의심"하는 습관 형성

### D6. `queries.py` 함수에서 파라미터 누락으로 SQL 바인딩 에러
- **S**: `available_lots()` 호출 시 "Incorrect number of bindings supplied" 에러
- **T**: 원인 파악
- **A**: 복사 과정에서 `fetch_dataframe()` 호출의 파라미터 인자가 누락된 것을 발견
- **R**: 누락된 인자 복구로 해결

## E. 시연 데이터 관리

### E1. 시연 데이터를 반복적으로 추천받고 재고 기준 재계산
- **S**: 각 공정 단계를 시연할 때마다 어떤 LOT을 얼마나 투입할지 판단 필요
- **T**: 실제 잔여재고를 확인하고 그에 맞는 수량을 다시 계산해야 함
- **A**: 매번 실제 잔여량 조회 쿼리를 먼저 실행하고, 그 결과 기준으로 투입 수량을 재조정
- **R**: 재고 부족으로 등록이 막히는 상황 없이 여러 차례 시연 성공

### E2. 잘못 등록한 데이터 삭제 방법 필요 (여러 차례)
- **S**: 시연 중 잘못된 값으로 등록한 실적을 지워야 하는 상황이 반복됨
- **T**: 계보·실적·검사결과까지 얽힌 데이터를 안전하게 삭제해야 함
- **A**: 자식 테이블(검사결과→생산실적→계보)부터 지우고 마지막에 LOT을 지우는 순서를 정리해서 매번 안내
- **R**: FK 제약 위반 없이 안전하게 삭제, 이후 스스로도 순서를 이해하고 적용

### E3. 설비 1대→2대 증설 시 기존 데이터/로직에 영향 있는지 사전 점검
- **S**: 공정별 설비를 늘리기 전에 기존 코드가 깨지지 않을지 확인하고 싶음
- **T**: 영향 범위 검토
- **A**: 모든 페이지가 `equipment_by_process()` 결과를 딕셔너리로 처리해 개수에 무관하다는 걸 코드 검토로 확인
- **R**: 안전하다고 확인 후 안심하고 증설 진행

### E4. 오래된 샘플데이터가 남아 불량현황 집계를 왜곡
- **S**: 프레스·노칭에서 손댄 적 없는 불량 기록이 계속 나타남
- **T**: 원인 파악
- **A**: 검사시각(`inspected_at`) 조회로 훨씬 이전 날짜의 샘플데이터 잔재임을 확인
- **R**: 해당 레코드 삭제로 정리, 이후 "이상한 값이 보이면 타임스탬프부터 확인" 습관 형성

- **S**: 마감을 앞두고 프로젝트 완성도를 스스로 판단하기 어려움

## G. Git / GitHub 실전 경험

### G1. 첫 GitHub 레포 구성 및 초기 업로드
- **S**: GitHub을 거의 안 써봐서 레포 생성부터 막막함
- **T**: 로컬 프로젝트를 새 레포에 올려야 함
- **A**: 레포 생성 → `.gitignore` 작성(DB 파일 제외) → `git init`/`add`/`commit`/`remote add`/`push` 순서로 단계별 진행
- **R**: 24개 파일 최초 업로드 성공

### G2. 비밀번호 인증 거부 및 토큰 발급
- **S**: `git push`에서 GitHub 비밀번호 입력 시 "Password authentication is not supported" 에러
- **T**: 대체 인증 수단 필요
- **A**: Personal Access Token 발급 절차(Settings → Developer settings → Tokens classic → repo 스코프)를 따라 진행
- **R**: 토큰으로 인증 성공, push 완료

### G3. 채팅창에 토큰을 실수로 노출
- **S**: 발급받은 토큰 문자열을 그대로 채팅에 붙여넣음
- **T**: 보안 위험 즉시 차단 필요
- **A**: 노출된 토큰을 즉시 폐기(delete)하고 새 토큰 재발급
- **R**: 보안 사고 확산 없이 마무리, 이후 토큰은 터미널에만 입력하는 습관 형성

### G4. 잘못된 토큰 권한으로 403 Permission denied
- **S**: 토큰으로 인증은 됐는데 `Permission denied` 403 에러 발생
- **T**: 원인 파악
- **A**: 토큰 생성 시 `repo` 스코프 체크가 제대로 안 됐을 가능성을 확인하고 스코프를 명확히 확인하며 재발급
- **R**: 정상 push 성공

### G5. DB 파일 대신 덤프 파일로 데이터 버전관리
- **S**: 실제 `.db` 파일을 커밋하면 안 된다는 걸 알지만 스키마+데이터는 남겨야 함
- **T**: 재현 가능한 형태로 데이터를 커밋할 방법 필요
- **A**: `sqlite3 db.db .dump > sql/dump.sql`로 스키마+데이터를 SQL 텍스트로 추출해 커밋
- **R**: DB 파일 없이도 누구나 동일한 상태를 재현 가능

### G6. `git commit --amend`가 "수정"이 아니라 "교체"임을 실전에서 체득
- **S**: 이미 push된 커밋의 메시지만 고치려다 `have diverged` 상황 발생
- **T**: 로컬과 원격이 갈라진 상태를 해결해야 함
- **A**: `amend`의 동작 원리(커밋 해시가 통째로 바뀜)를 이해하고 `git push --force`로 원격을 로컬 기준으로 정리
- **R**: 정상적으로 동기화, 이후 amend 시 항상 force push가 필요하다는 걸 체득

### G7. 여러 파일을 하나로 커밋했다가 메시지별로 분리하고 싶어짐
- **S**: `journal.md`와 `requirements.txt`를 한 커밋에 같이 올렸는데 메시지를 따로 남기고 싶어짐
- **T**: 이미 만들어진 커밋을 분리해야 함
- **A**: `git reset --soft HEAD~1`로 커밋만 취소(파일 내용은 유지)하고, 파일별로 나눠서 다시 커밋
- **R**: 원하는 대로 메시지가 분리된 커밋 구조 확보

### G8. VSCode 소스 제어로 전환, amend를 GUI로 수행
- **S**: 터미널 명령어 대신 VSCode에서 같은 작업을 하고 싶어짐
- **T**: 소스 제어 패널 사용법 습득 필요
- **A**: Stage/Commit/Push 버튼 대응 관계를 익히고, 명령 팔레트로 `Git: Commit (Amend)`, `Git: Force Push` 실행
- **R**: GUI로도 동일한 작업 수행 가능해짐, 터미널과 혼용 가능함을 확인

### G9. 첫 커밋 메시지를 나중에 다시 수정 (rebase)
- **S**: 이미 여러 커밋이 쌓인 뒤에 맨 처음 커밋의 메시지를 바꾸고 싶어짐
- **T**: `amend`는 최신 커밋만 가능해서 다른 방법 필요
- **A**: `git rebase -i --root`로 전체 커밋 목록을 불러와 첫 커밋만 `reword`로 지정 후 메시지 교체
- **R**: 이후 이어지는 모든 커밋이 자동으로 재구성되며 성공적으로 수정, `--force` push로 반영

### G10. 로그인 정보를 매번 새로 물어보는 문제
- **S**: `git push`할 때마다 토큰을 다시 입력해야 해서 번거로움
- **T**: 인증 정보를 기억하게 만들 방법 필요
- **A**: `git config --global credential.helper store` 설정
- **R**: 이후 push 시 재인증 없이 진행 가능

## 정리

이 목록을 다시 훑어보면, 문제의 성격이 크게 세 갈래로 나뉜다.

1. **데이터가 쌓이면서 드러난 설계 허점** (A1, A2, A4) — 처음엔 안 보이다가
   여러 배치·여러 날짜가 쌓이고 나서야 발견된 것들. 가장 깊이 있는 소재.
2. **프레임워크(Streamlit) 동작 원리를 몰라서 생긴 문제** (B1~B7) — 문서를
   찾아보거나 직접 원인을 추적해서 해결한 것들.
3. **도구 사용 경험 자체의 성장** (G1~G10) — Git을 거의 안 써봤다가, 이
   프로젝트를 통해 rebase, force push, credential 관리까지 다뤄본 것.
